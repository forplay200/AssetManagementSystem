# FYP 讨论建议：侵权风险、删除治理与 Audit Trail

日期：2026-10-26（Asia/Kuala_Lumpur）

状态：**供用户、老师与后续 Agent 讨论的建议稿；尚未确认全部规则，未实施。** 不得把本文描述成系统已有能力，不得直接按本文修改业务代码或新增管理员权限。

英文版本：[English version](fyp-copyright-deletion-audit-recommendations.en.md)。

相关已选目标：[视频资产支持范围](video-asset-support-scope-plan.md)。英文术语是 **copyright infringement** 与 **audit trail**。

## 1. 核心建议

1. 侵权风险不能靠平台保证完全消失，但应有预防、投诉响应与追溯机制；Terms and Conditions 不是自动免责证明。
2. 回收站解决恢复窗口，audit trail 解决操作追溯，审批/异议规则解决谁能决定永久删除。三者不能相互代替。
3. 推荐普通删除采用“软删除 + 通知 + 保留期”；若要保护 Manager 对 Owner 删除的异议，则还需明确冻结与处理机制。
4. “Manager 必须同意才删除”与“Manager 不回应几天后自动删除”不是同一种规则。后者应称为“通知与异议窗口”，不得把沉默记录成同意。
5. 涉嫌侵权的访问限制与普通回收站恢复分开处理，不能通过 Restore 按钮重新公开受限制的内容。

## 2. 当前已核对的能力与缺口

本次读取 `backend/src/controllers/assetsController.js` 的 `deleteAsset`：检查资产删除权限后，清理资产及版本的对象文件，再删除版本与 Asset 数据。该路径没有提供本建议中的回收站保留窗口。

读取 `backend/src/models/asset.js` 未发现本建议的回收站状态字段。这里不声称已经全面审计仓库的所有日志或运维能力；只能确认现有资产删除路径不能据此宣称“可恢复删除”。

当前权限基线：

- Owner 可管理当前 Workspace 的任何 Asset。
- Manager 只能修改/删除本人首次上传的 Asset；共享词库管理保留原例外。
- Collaborator 下载限制已在相关交接文档标记实施，预览与评论保留。
- System Administrator 的现有角色不能直接推导为有权读取任何 Workspace 资产。

后续若采纳删除保护，本质是为 Owner 的不可逆删除增加流程限制。其他资产编辑权限不应被顺带更改。

## 3. 侵权：应如何定义系统责任

### 3.1 区分身份与权利

| 概念 | 本系统应如何理解 |
| --- | --- |
| Workspace Owner | 应用中的管理角色，不自动证明著作权归属 |
| Asset uploader | 系统中的上传者，不自动等于作者或著作权人 |
| Copyright holder / licensor | 需要结合授权、合同及适用规则判断的权利主体 |
| AI visual tags | 对内容的辅助描述，不是授权认证或侵权检测结论 |

用户自己制作的游戏录像也可能包含第三方音乐、图像或模型。来源和授权记录应允许描述不同组成部分，而不能用“我录制的”自动推断所有内容均获授权。

### 3.2 建议的预防措施

- 上传声明：用户确认有权在该 Workspace 中储存、向成员提供访问，并按项目用途处理文件；不能仅问“是不是你原创”。
- 来源 metadata：来源类型、作者/权利人声明、来源链接、许可名称与版本、允许用途、署名要求、必要的授权依据。
- 未经核验的声明标为“用户声明/未核验”，不能显示“平台已验证合法”。
- 对 AI 内容分析说明用途；本项目目标是推理生成标签，不应暗示会使用用户资产训练模型。实际实现与政策保持一致。
- Workspace 访问和下载权限在后端执行；保留预览的同时，不把隐藏下载按钮描述成防止复制或侵权。
- 演示与评估使用自制、明确获授权或许可允许相应用途的资产，并保留必要来源信息。

条款应说明允许用途、禁止未经授权上传、投诉处理方式、限制访问/删除流程及用户申诉渠道。不能写成“所有责任都属于用户，因此平台没有责任”。

### 3.3 建议的投诉处理流程

```text
投诉/通知到达指定联系渠道
  → 记录涉及资产、投诉依据、时间和案件编号
  → 由指定处理人员核查并按适用程序决定限制访问
  → 通知上传者并允许提交授权依据/申诉
  → 按处理结果恢复访问或处置内容
  → 留下必要、受权限保护的处理记录
```

- 外部权利人不一定是 Workspace 成员，因此不能只提供登录后才能使用的投诉入口。
- 不向投诉者泄露整个私有 Workspace；只接收其能提供的资产线索和权利依据。
- “限制访问”不等于立即销毁证据。保留什么、谁能访问及保留多久需有明确、受限的政策，不无限期保存所有原文件。
- 需要指定平台运营层面的投诉联系人/处理责任。该职责尚未确定，不能自动授予现有 System Administrator 全部资产访问权，也不能让被投诉的 Owner 成为唯一处理人。
- 简单网页表单或人工处理登记可作为 FYP 初步范围，但若没有实际访问限制和结果记录，答辩时不能称为完整 takedown 系统。
- 不依赖普通回收站的 7 天候选保留期来决定法定通知的响应时间。

### 3.4 法律依据的使用边界

MyIPO 公开的《Copyright Act 1987》文本标注截至 2022-06-30。其 Part VIB 涉及服务提供者责任限制；43G 涉及投诉联系信息，43H 涉及通知、移除/禁用访问及反通知程序。由此可以说明：不能只凭一份用户条款，就推断平台自动获得免责。[MyIPO 法案文本](https://www.myipo.gov.my/wp-content/uploads/2025/02/Lampiran-A1-ENG-Akta-Hak-Cipta-setakat-22-Jun-2023.pdf)

本文提供 FYP 风险控制设计建议，不认定项目符合某项法律保护。正式运行时需核实适用法律、当时有效文本和具体事实；网页/文件发布日期不能当成法律修订日期。项目内部投诉处理流程也不能自行取代适用的法定程序。

## 4. 删除治理：推荐如何收敛用户原想法

### 4.1 普通回收站基础方案

1. 将 Delete 改为 Move to recycle bin，确认框说明影响、保留期限和恢复方式。
2. Owner 可软删除当前 Workspace 任意资产；Manager 可软删除自己上传的资产。
3. 资产从正常列表、搜索与常规内容读取路径移除；保留文件、历史版本、关联 metadata 和恢复所需数据。
4. Owner 删除其他上传者的资产时要求填写原因，并持久记录通知给原上传者。
5. 候选保留期为 7 天，具体天数尚待确定。保留期不是法律期限，也不代表用户已经选择 7 天。
6. 普通、未受限制且无争议的资产，可由 Owner 或仍有该资产管理权限的原上传者恢复；恢复行为也记录。
7. 建议第一版统一禁止保留期内手工永久清除，避免增加“立即删除”旁路。若未来允许提前删除，需要另行定义权限、知情确认和审计规则。
8. 到期、无 hold、无争议且满足处理条件时，由后台任务执行永久清理。

这个基础方案能够减少误删损失，但仅靠它还不能保证 Manager 有权否决 Owner 的删除。

### 4.2 若要保护 Manager 异议：增加 Disputed 状态

用户原想法包含降低 Owner 任意删除他人资产的影响。建议把它明确表述为：

> Owner 可以先把资产移入回收站，但不能立即不可逆地清除。原上传者可以在保护窗口内提出异议；异议发生后暂停自动清理，等待规定的处理结果。

建议状态示意：

```text
Active → Trashed → Purging → Purged
             ↓
          Disputed
             ↓
       经明确处理后恢复，或重新安排清理

Trashed → Active：仅适用于允许普通恢复的情况
```

- 无回复不是同意；自动清理的 reason 应为 `retention_expired_without_objection`，不能伪造 `approved_by_uploader`。
- 收到异议后停止计时清理，Owner 不能独自解除针对自己删除行为的异议冻结。
- 由于独立裁决角色尚未定义，FYP 可先采用“双方一致处理，否则保留冻结并报告未解决状态”的有限机制。它有储存与长期未决的代价，应明确写入 limitations。
- 若需要最终强制裁决，必须另行指定中立处理者、权限与申诉规则；不能在实现时由 Agent 擅自赋予现有系统管理员此权力。
- 解除冻结后若仍要清理，应重新通知并给予明确处理窗口，不能因为旧期限已过而立刻删除。
- 用户仍有管理权限时可普通恢复；一旦处于侵权限制、保全或争议处理状态，走专门流程，不允许通用 Restore 绕过。

### 4.3 最容易被 moderator 追问的绕过路径

- **Owner 先移除或降级 Manager，再等待删除：** 成员变化不能自动算作同意或取消已有异议；待处理的他人资产删除遇到上传者失去处理权限时，应暂停自动清理，转入明确处理流程。
- **Owner 删除整个 Workspace：** Workspace 删除不能绕过资产保护期、争议/投诉限制或审计留存。
- **原上传者注销、离开或账号被停用：** 不恢复其 Workspace 内容权限；其待处理事项需要定义独立申诉或人工处理路径，不能假设能继续点击站内按钮。
- **Owner 反复删除、Manager 反复恢复：** 需要记录每次状态变更并允许进入争议处理，不能无限刷新保护期后声称问题已解决。
- **通知失败或用户未登录：** 区分通知已入站、已投递、已阅读。建议持久通知创建失败时不启动自动清理；创建成功不等于阅读或同意。
- **Owner 修改保留时间：** 不允许通过缩短 Workspace 设置提前清除已经进入保护期的资产。
- **有人拥有数据库/服务器权限：** 应用权限无法保证抵抗这些特权操作。需要额外运维控制，不能宣称完全防篡改。

只有这些路径也受到约束，才适合声称“限制 Owner 绕过保护窗口”；否则应准确称为“减少误删并提高可追溯性”。

## 5. Audit trail：记录什么，以及不应承诺什么

Dashboard 只是记录的展示位置。建议由后端在业务操作发生时生成独立事件，不能依靠前端成功 toast 或浏览器日志。

每条事件建议包括：

| 字段 | 用途 |
| --- | --- |
| eventId、request/correlationId | 识别事件、关联重复请求和后台任务 |
| serverTime（UTC） | 记录服务端发生时间，界面按本地时区展示 |
| actorId、actorRoleSnapshot、actorType | 区分用户与系统任务，保留当时角色 |
| workspaceId、assetId、assetNameSnapshot、versionId（适用时） | 资产改名或删除后仍能辨认对象 |
| action、reason、outcome | 区分软删除、恢复、清理请求、成功、失败、拒绝 |
| beforeState、afterState、scheduledPurgeAt（适用时） | 说明状态变化和计划期限 |

最低事件范围建议为软删除、恢复、通知创建、异议提出/处理、永久清理请求/完成/失败及相关成员权限变更。后续按研究范围加入标签、metadata、版本及名称变更。

设计要求：

- Workspace Owner/Manager 不能通过业务 API 修改或删除这些事件；普通用户只读取授权范围的记录。
- 审计事件不能随 Asset 或 Workspace 外键级联删除。名称采用有限快照，不保留不必要的完整敏感内容。
- “后台任务完成删除”记录 system actor，同时关联原发起者；不把定时任务执行时间冒充 Owner 点击时间。
- 资产状态与必要审计/待通知记录尽量在同一数据库事务中写入，防止删除成功却没有记录。
- 对象存储清理不能假装与数据库原子提交；采用可重试的 Purging 状态，所有目标对象清理完成后才记 Purged。
- 清理含当前文件、所有版本、视频封面/抽帧及其他衍生对象；处理共享对象时防止误删仍被引用的资源。
- 为审计另设留存和访问政策；保留审计摘要不等于永久保留被删除原文件。
- 不记录密码、token、签名下载链接、完整授权凭证或投诉者敏感信息到普通 Dashboard。
- 应用层追加事件和限制 API 不等于数据库管理员无法篡改。更强需求另行评估独立日志存储、权限分离和篡改检测。

OWASP 建议日志能够回答何时、何处、谁做了什么，并保护记录免受未授权修改与删除，也提醒排除凭证等敏感信息。以上具体事件与状态机是本项目的设计建议。[OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

## 6. 侵权限制与回收站如何配合

建议把内容访问限制与文件生命周期分别表达，不用一个 deleted 布尔值兼任所有含义：

- 生命周期：Active / Trashed / Disputed / Purging / Purged。
- 访问限制：正常 / 投诉处理中受限 / 其他经授权的限制。
- 清理 hold：是否禁止清理、原因、设定者及复核状态。

这些是概念字段，不是已批准的数据库 migration。

例如：收到投诉后，资产可以仍有储存记录，但普通预览和下载被限制；即使 Owner 或上传者恢复回收站状态，也不能自动解除投诉限制。原视频受限时，历史版本及封面/抽帧等衍生访问也应一并检查。

内部保留期与投诉程序分别处理。既不能用自动清理销毁待处理证据，也不能以“有争议”为由无限期保留所有内容；必须定义复核、保留与处置责任。

## 7. 建议的 FYP 优先顺序与验收

### 第一阶段：建议优先完成

- 上传授权声明与来源/许可 metadata。
- 明确投诉联系渠道与处理责任，至少能登记并追踪处理状态。
- 普通软删除、回收站、恢复、持久通知、保留期限。
- 独立审计事件与 Dashboard/详情历史展示。
- 侵权访问限制与普通恢复的隔离。

### 第二阶段：若要主张对 Manager 的更强保护

- 异议冻结与双方处理流程。
- 成员移除、Workspace 删除、保留期变化等绕过路径的约束。
- 失去成员身份后的申诉和未决争议处置机制。

没有第二阶段时，不应在答辩中承诺“Manager 可以阻止 Owner 永久删除”。

### 必要验证例子

1. Owner 删除 Manager 的资产后，文件及历史版本在保护期内可按权限恢复。
2. 删除后的资产不能经列表之外的旧 URL、版本和衍生预览路径继续普通访问。
3. Manager 不能操作另一 Manager 的资产；Collaborator 下载限制保持。
4. 若实现异议，冻结期间清理任务及 Owner 手动路径均无法永久清除。
5. 降级/移除上传者、删除 Workspace、缩短期限不能绕过已声明的保护。
6. 部分对象清理失败时显示未完成并可重试，不产生虚假的成功审计事件。
7. 删除/改名后的资产仍有可理解的事件记录，且无跨 Workspace 泄露。
8. 普通恢复不能解除投诉访问限制；通知失败和长时间未登录有明确处理结果。

## 8. 可用于老师询问的回答

下列用“计划/拟采用”描述尚未实现内容。完成并验证后，才能改成“系统已经”。

### Q1：用户上传侵权内容怎么办？

> 我不能保证用户上传的每份资产都没有侵权，也不会仅凭用户条款就声称平台免责。我计划结合上传授权声明、来源与许可记录、Workspace 访问控制，以及投诉后的核查和限制访问流程来降低风险。系统的 AI tagging 只帮助描述和查找内容，不判断版权归属。对于无法由系统自动确认的授权问题，会保留人工处理和申诉渠道。

### Q2：Owner 擅自删除 Manager 上传的资产怎么办？

> 目前删除流程仍有直接清理文件的风险，所以我提出回收站设计：Owner 的删除先成为可恢复的软删除，并通知上传者、记录原因和时间。如果进一步加入异议保护，上传者提出异议后会暂停永久清理。这样可以减少立即丢失资产的风险，并留下可追溯记录；它不代表上传者自动拥有著作权，也不代表系统能解决所有团队争议。

### Q3：到底是 Manager 同意才能删除，还是过几天自动删除？

> 这两种政策不同。如果采用到期自动清理，我会明确称为通知与异议窗口：没有异议才按预先说明的期限清理，沉默不记录成同意。若要求必须明确同意，就不能因为超时而自动删除。我倾向先评估前一种方案，并补上异议冻结与处理规则。

### Q4：Dashboard 有记录就能防止滥用吗？

> Dashboard 提供可见性，真正的记录应在后端生成并独立保留。审计日志用于追踪责任，回收站用于恢复，权限和冻结规则用于约束操作。三者各自解决一部分问题，我不会声称日志本身就能阻止所有删除，或抵抗拥有数据库管理权限的人。

### Q5：这样是不是削弱 Owner？

> 是对不可逆操作增加程序约束。Owner 仍负责 Workspace 管理，但删除他人上传的资产需要留下原因、通知和恢复窗口；如果采用异议机制，还需要按约定处理争议。应用管理角色与资产版权归属是不同概念。

### Q6：为什么不等 Manager 同意之后才移除涉嫌侵权内容？

> 普通团队删除与侵权投诉处理需要分开。访问限制应由明确的处理责任和适用程序决定，不能被普通删除审批拖延；是否保留文件、是否允许恢复，则按独立的处理与保留规则执行。

## 9. 后续需要用户决定的政策

本节只是记录待决事项，不代表本次需要暂停等待回答：

- 保留期的长度及通知规则。
- 先做基础回收站，还是同时实现异议冻结。
- 未决争议的处理者、权限、时限与无法达成一致时的处理方式。
- 上传者离开/被移除后的申诉路径。
- 投诉处理责任人与必要、受限的访问权限。
- 审计及投诉记录的查看范围、保留期限、处置规则。
- 是否需要未来的提前永久删除，以及防止绕过保护的条件。

下一步应先确认这些产品规则，再编写精确实施交接、状态迁移与权限测试。不得把本建议中的候选数值或角色安排当成用户已经批准的最终政策。
