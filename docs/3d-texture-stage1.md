# 3D 材质与贴图：第一阶段使用说明

日期：2026-10-08。

第一阶段代码已实现，前后端已用 Docker 重新编译并启动。编译成功，后端启动日志确认数据库同步完成。真实 OBJ / FBX 样本导入、跨设备预览及历史包完整性尚待实际验收；本次没有创建或执行测试。

## 1. 目前可以做什么

- 把主模型、材质和贴图作为一个资产上传。
- 检查模型引用的附件，显示缺失、同名冲突、不支持格式及 UV 提示；可以手动选择引用对应的文件。
- 在上传前本地预览，以及在资产详情中查看基础材质和贴图。预览可以切换材质显示与几何显示。
- 下载包含模型和附件的 ZIP，也可以单独下载未经改写的原始主模型。
- 只更新材质或贴图，复用当前主模型；更新前的完整文件包保留为历史版本。
- 在 Versions 中预览和下载历史模型包。

浏览器显示贴图与服务器 AI 分析是两条流程。当前 CLIP 检查点保持 `openai/clip-vit-base-patch32`，3D AI 仍走现有几何分析；真实贴图渲染及颜色、材质外观标签属于第二阶段。

## 2. 新模型怎样上传

### OBJ

准备 `.obj`、它引用的 `.mtl`，以及 MTL 实际使用的 PNG / JPG / JPEG 图片。例如：

```text
chair.obj
chair.mtl
textures/chair_diffuse.png
```

1. 打开 Upload，选择 `chair.obj`。
2. 在 **Materials and textures** 区域点击 **Add companion files**，选择 MTL 和贴图，也可以把附件拖入该区域。
3. 查看引用列表。系统先按路径寻找附件，再在文件名唯一时自动关联。缺失文件就补选；同名冲突就填写不同的 **Relative path**，并在引用下拉框中指定对应文件。
4. 点击 **Preview model**，确认基础颜色与贴图效果。模型需要相应材质和 UV，单独提供一张图片不会自动产生正确的贴图坐标。
5. 点击上传。文件保存成功与 AI 排队状态分别显示。

普通多文件选择通常只有文件名。可以在 Relative path 中填写 `textures/chair_diffuse.png`；目前没有 ZIP 或文件夹自动导入。

### FBX

1. 选择 `.fbx` 主模型。
2. 如果导出时已嵌入受支持的 PNG / JPEG 图片，页面会显示检测到的内嵌图片；以实际预览效果确认是否正确加载。
3. 如果模型引用外部贴图，通过 **Add companion files** 补选图片，再处理缺失或名称冲突。
4. 点击 **Preview model** 确认后上传。

MTL 用于 OBJ；FBX 不接收 MTL 附件。FBX 导出版本、材质及内嵌图片的兼容性由现有 Three.js 加载器和本阶段引用解析共同决定，复杂着色器不能保证复现。

### 暂时没有完整材质

可以明确勾选 **Upload geometry only**。这个版本使用几何显示；已提供的受支持附件仍保留在下载包内。缺少或冲突的引用会继续记录，不会被当作完整材质。

无效主模型、非法路径和超出上传预算不能通过该选项绕过。TGA / DDS 等不支持的附件目前不会接收；应先转成 PNG / JPEG 或等后续格式扩展。

## 3. 已有模型怎样补充或更换贴图

具有资产管理权限的 `workspaceOwner` / `workspaceManager` 可以执行：

1. 打开资产详情，点击 **Update materials / textures**，或者在 **Versions** 中点击同名按钮。
2. 页面读取当前主模型及附件。主模型会复用，保存时无需重新上传。
3. 点击附件旁的 **Replace** 更换文件；也可以添加、移除附件或调整引用。未更换的附件会随新版本一起保存。
4. 点击 **Preview model**，确认新外观。
5. 填写 **Version note**，点击 **Save version**。

系统创建新的文件包，更新当前资产，并把修改前的完整包保留为历史快照。历史版本继续引用当时的主模型、MTL 和贴图，不会使用当前版本的附件。

已有的单文件资产继续可用。对旧 OBJ / FBX 使用上述入口补齐附件后，会形成有资源清单的新模型包。

## 4. 下载和版本

- 模型包的 **Download ZIP** 包含主模型、全部附件和 `aether-package.json` 清单。
- ZIP 保留编辑器中的逻辑路径，并按已确认的绑定重写导出副本的 OBJ / MTL / FBX 资源路径，减少对原电脑绝对路径的依赖。
- **Original main file** 下载存储中的原始主模型，文件内容保持不变；没有附件的原始主模型可能无法在其他设备单独显示贴图。
- **Preserve snapshot** 保存当前完整包，不改变当前资产。
- **Upload new version** 替换主文件及其附件；旧包先保留为快照。
- 历史版本的 Preview / Download ZIP 使用该版本自己的文件包。

ZIP 导出是本阶段功能，ZIP 重新导入属于后续阶段。

## 5. 当前限制

| 项目 | 限制 |
|---|---|
| 主文件 | 50 MB |
| MTL | 每个 2 MB |
| 外部贴图 | PNG / JPG / JPEG，每张 10 MB |
| 附件 | 最多 32 个 |
| 完整上传包 | 100 MB |
| 图片像素 | 每张最多 16,777,216；内嵌和外部图片合计最多 67,108,864 |
| 浏览器预览图片 | 长边超过 2048 时缩小；下载仍提供原图 |
| 材质范围 | 基础颜色、漫反射贴图及现有加载器可处理的基础材质；完整 PBR / 原软件节点材质不在本阶段保证范围 |

这些是初始资源预算，尚未测量 RTX 4060 laptop 或云端的实际内存、显存与帧率表现。图片解码像素限制由后端再次校验；内嵌 FBX 图片同样受图片预算约束。

## 6. 本次实现与部署

- `Asset.packageManifest`、`Version.packageManifest` 新增可为空的 JSONB 字段，旧单文件数据可继续读取。
- 原始资源按工作区、资产和独立包 ID 保存到 MinIO；逻辑路径单独放在清单中，更新不覆盖旧包。
- 当前与历史附件均通过登录和工作区资产权限读取；前端先获取认证 Blob 再交给 Three.js，模型引用不会触发任意外部网址或本机路径读取。
- 多文件接收改用临时磁盘和流式大小限制；保存失败时清理本次未提交的文件。
- ZIP 导出增加 `yazl` 依赖；后端镜像使用 Node 22，以满足现有 `sharp` 图像处理依赖的运行要求。
- 执行 `docker compose up -d --build --no-deps backend frontend`，已重建并启动前后端。数据卷未删除。

目前刷新网页即可使用新版；无需再次重建。
